# SEC-005 — Secure retention of original case documents

Date: 2026-10-28
Status: DESIGN ONLY — no storage bucket, policy, migration, or production setting changed.

## Current behavior observed

The `analyzeDocument` server function accepts PDF or image data (maximum 8 MiB), checks that the authenticated user owns the case, sends the content to the AI provider, and stores the extracted summary as a `user_document` case step. Its source comment explicitly says the original file is not stored. The step stores the supplied file name and summary, not a retrievable original.

This creates a functional gap if the user later needs to prove exactly what an authority sent, compare OCR/AI extraction against the source, or download the original.

## Target design

- Store originals in a private Supabase Storage bucket; never use a public bucket for administrative/legal documents.
- Use opaque object paths generated by the server, for example `{user_id}/{case_id}/{document_id}`; never trust a client-supplied path.
- Verify session, case ownership, and access on every upload, list, read, signed-URL issuance, replacement, and deletion operation.
- Storage policies must enforce ownership and case relationship. Do not assume UI checks are sufficient.
- Store metadata in a database row: document UUID, case UUID, owner/user UUID, storage object key, original filename (sanitized), MIME type, byte size, SHA-256 checksum, upload timestamp, retention status, and optional extraction-step ID.
- Keep the original immutable after upload. A replacement should create a new version/document record and preserve the previous checksum/metadata unless an approved retention policy requires deletion.
- Restrict allowed MIME types and enforce byte limits on both client and server. Do not trust filename extensions or browser-provided MIME type alone; inspect file signature where feasible.
- Issue short-lived signed download URLs only after authorization. Do not log signed URLs, file bytes, access tokens, or extracted sensitive text.
- Record access/deletion events with minimal metadata; avoid duplicate copies of sensitive content in audit logs.
- Define retention and deletion rules explicitly. For official evidence, never silently delete originals due to an application retry, AI failure, or summary regeneration.
- Treat AI extraction as derived data, not as the authoritative original. Display a clear link from summary to its source file and preserve uncertainty/illegible markers.

## Acceptance tests

1. Anonymous user cannot upload, list, or download.
2. User A cannot read User B's file even if they know a case/document UUID or object path.
3. A non-owner cannot mint a signed URL for a document.
4. Invalid MIME/signature, oversized file, path traversal, and malformed identifiers are rejected.
5. Repeated upload request with the same document request ID does not create uncontrolled duplicates.
6. The stored checksum matches the exact original bytes and remains stable after summary regeneration.
7. AI/provider failure leaves the original document intact and retryable.
8. Deletion follows an explicit policy and leaves required audit metadata without leaking content.
9. A case summary links to the correct original and records extraction version/time.
10. Integration tests run against an isolated staging project, not the production bucket.

## Rollout gates

- Read-only inventory of current Storage buckets, policies, tables, and existing document references.
- Agree retention period and whether user-initiated deletion is allowed for administrative evidence.
- Design a reversible staging migration and test both Storage policies and database RLS.
- Explicit user approval before production schema/policy changes.
- Mark SEC-005 VERIFIED only after staging acceptance tests pass.

No production changes have been applied.
